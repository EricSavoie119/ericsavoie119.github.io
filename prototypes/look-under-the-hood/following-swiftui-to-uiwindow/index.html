Look Under the Hood 02

Following SwiftUI from App.main() to UIWindow

Using LLDB to trace the launch path SwiftUI normally keeps out of sight.

9 min read · July 2026 · SwiftUI LLDB
The trail we're following
@main App → App.main() → runApp() → UIApplicationMain → AppSceneDelegate → UIWindow

In Part 1 we rebuilt a SwiftUI “Hello, world!” in UIKit. We ended with a useful mental model—but also a loose end: does SwiftUI really travel through the same UIKit machinery?

There is only one satisfying way to answer that. We are going to stop the app while it launches, walk the stack, inspect the values being handed to UIKit, and follow the scene lifecycle until a window appears.

How does .main() eventually cause UIKit to create a window?

swift · HelloWorldApp.swift 
import SwiftUI

@main
struct HelloWorldApp: App {
    var body: some Scene {
        WindowGroup {
            Text("Hello, world!")
        }
    }
}

Break at the UIKit boundary

A line breakpoint pauses at a line of source code that we own. A symbolic breakpoint pauses when a function with a particular name is entered—even when we do not have that framework's source.

UIApplicationMain is a useful first target because it is the public UIKit boundary we used explicitly in Part 1:

lldb · symbolic breakpoint 
UIApplicationMain
  1. Prepare a fresh launch

    Select the SwiftUI app's scheme and an iPhone simulator, then stop the app if it is already running. We need to catch the launch path from its beginning.

  2. Open the Breakpoint navigator

    Press ⌘8, or choose the breakpoint-shaped icon in Xcode's Navigator area.

  3. Create a symbolic breakpoint

    Click the + button at the bottom of the navigator and choose Symbolic Breakpoint….

  4. Enter the symbol

    Type UIApplicationMain in the Symbol field. Leave Module and Condition empty so the breakpoint can resolve regardless of where UIKit exposes the symbol.

  5. Keep the breakpoint paused

    Make sure the breakpoint is enabled and that Automatically continue after evaluating actions is off. Close the editor by clicking elsewhere.

  6. Run the app

    Press ⌘R. Xcode should pause before the first SwiftUI screen appears. Seeing assembly rather than source is normal: we stopped inside a framework function.

  7. Open the debug console

    Press ⇧⌘Y to show the Debug area. Click the console prompt and enter bt, short for “backtrace”.

  8. Read and save the stack

    The newest frame is at the top. Read upward from the bottom to follow launch toward UIApplicationMain, then copy the console output so we can compare it with the trail below.

If the breakpoint does not stop Check that its name is exactly UIApplicationMain, that the breakpoint is enabled, and that you performed a fresh launch rather than attaching to an app that was already running.

When the breakpoint hits, copy the stack trace. A representative result looks like this:

lldb · stopped stack 
#0  UIApplicationMain
#1  closure in SwiftUI.KitRendererCommon
#2  SwiftUI.runApp
#3  static SwiftUI.App.main()
#4  static HelloWorldApp.$main()
#5  main
#6  start

Addresses and exact symbol spelling will differ. The order is what matters: our generated entry point calls SwiftUI's App.main(), SwiftUI moves through its renderer setup, and the path reaches UIApplicationMain.

EVIDENCE 01 @main enters SwiftUI The compiler-generated $main frame leads into the static method supplied by App.
EVIDENCE 02 SwiftUI enters UIKit UIApplicationMain is on the live launch stack, not merely a conceptual comparison.
EVIDENCE 03 The process does not return The renderer hands off to the application event loop that keeps the app running.

Follow the generated $main

The $main suffix tells us we are looking at compiler-generated code for the type marked with @main.

Step into that frame and two jobs become visible:

  1. Swift obtains the protocol conformance information for HelloWorldApp: App.
  2. It calls the static App.main() implementation supplied by SwiftUI.

That lines up with the language model from Part 1. The @main attribute does not itself know how to launch an iOS app. It identifies the type whose static main() should run; SwiftUI provides that method.

Keep the layers separate @main is the Swift entry-point mechanism. App.main() is SwiftUI's launch implementation. UIApplicationMain is the UIKit boundary that starts the application.

Inspect the handoff to UIKit

Now stop again at UIApplicationMain. On an arm64 run, the first four function arguments are passed in registers x0 through x3.

UIApplicationMain at the breakpoint
Register Meaning
x0 argc — the argument count
x1 argv — the argument vector
x2 The principal application class name
x3 The application delegate class name

Read all four at once:

lldb · registers 
register read x0 x1 x2 x3
po (NSString *)$x2
po (NSString *)$x3

In the run captured for these notes, the final two values resolved to private SwiftUI types equivalent to:

principal class → SwiftUI.SwiftUIApplication delegate class → SwiftUI.AppDelegate

This is the first real payoff. SwiftUI did not bypass UIKit's application launch. It supplied its own internal application and delegate types to UIKit.

! If you run on a different architecture, the calling convention and registers differ. Treat the commands above as an arm64 example and verify the active architecture before interpreting raw registers.

The missing window

At this point I expected SwiftUI's app delegate to create a UIWindow inside application(_:didFinishLaunchingWithOptions:).

It did not.

Looking up and disassembling that method showed launch-option handling and Objective-C bridging, but no obvious window creation, root view controller, or makeKeyAndVisible().

Dead end?
No. The missing window is evidence that we are looking in the wrong lifecycle callback.

The clue is another method on the same private delegate:

lldb · symbol lookup 
image lookup -rn "AppDelegate.*configurationForConnecting" SwiftUI

application(_:configurationForConnecting:options:) is the handoff from the app lifecycle to the scene lifecycle. SwiftUI's public WindowGroup had been pointing us toward scenes from the beginning.

A note about addresses and ASLR

Symbol lookup may give you an offset inside the SwiftUI image rather than the runtime address you can disassemble directly. That is because Address Space Layout Randomization loads the framework at a different address between runs.

The useful workflow is:

lldb · resolve a private symbol 
# Find the symbol and its image-relative offset
image lookup -rn "AppDelegate.*configurationForConnecting" SwiftUI

# Find where SwiftUI was loaded for this run
image list -o -f SwiftUI

# Disassemble the resolved runtime address
disassemble -a <load-address + symbol-offset>

Do not copy an address from an article and expect it to work. Recalculate it for the process you are debugging. The arithmetic is disposable; the method is reusable.

Follow the scene trail

Searching the SwiftUI image for scene-related delegate symbols turns up an internal scene delegate and methods associated with connecting and hosting a scene.

lldb · continue the search 
image lookup -rn "SwiftUI.AppSceneDelegate"
image lookup -rn "makeSceneHostWindow" SwiftUI

Following those symbols gives us the scene half of the launch path:

SwiftUI.AppDelegate → application(_:configurationForConnecting:options:) → SwiftUI.AppSceneDelegate → scene(_:willConnectTo:options:) → makeSceneHostWindow(...) → UIWindow

We can now explain why didFinishLaunchingWithOptions did not contain the window setup. The process-level delegate configures a scene; the scene delegate owns the UI instance and creates its window.

The host object that connects the SwiftUI hierarchy to that window is private implementation. Depending on the framework version, the symbols and internal types can move. The public architectural boundary is the durable conclusion: SwiftUI uses UIKit's scene and window infrastructure to present the interface.

The recovered launch chain

Putting the evidence together, our observed path looks like this:

@main HelloWorldApp → compiler-generated HelloWorldApp.$main() → static SwiftUI.App.main() → SwiftUI.runApp() → SwiftUI.KitRendererCommon(...) → UIApplicationMain( argc, argv, "SwiftUI.SwiftUIApplication", "SwiftUI.AppDelegate" ) → AppDelegate.configurationForConnecting(...) → AppSceneDelegate.scene(_:willConnectTo:) → makeSceneHostWindow(...) → UIWindow appears

Compare that with the public SwiftUI code:

@main App → WindowGroup → Text("Hello, world!")

SwiftUI is not removing the application lifecycle. It is compressing that lifecycle into a declarative model and managing the UIKit objects on our behalf.

What was actually useful here?

The private class names are interesting, but they are not the lesson. The useful part is the investigation pattern:

  1. Start with a narrow question.
  2. Find a known public boundary such as UIApplicationMain.
  3. Capture the stack before stepping blindly.
  4. Classify each frame by layer: app, language, SwiftUI, UIKit.
  5. Inspect arguments at the boundary.
  6. Let missing evidence redirect the search.
  7. Distinguish a supported architecture from a private implementation detail.
The real under-the-hood skill Do not memorise the internals you find. Learn how to find them again, and how to decide which conclusions are safe to carry back into production code.
